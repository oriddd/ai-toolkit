# iOS privacy manifest (`PrivacyInfo.xcprivacy`) from `app.config.ts`

Apple rejects (or emails about) uploads whose binary uses a required-reason API without a declared reason, and expects
the app's collected data types to match its privacy label. In a managed Expo app the manifest is generated from
`ios.privacyManifests`; never edit `ios/` by hand (it is regenerated by prebuild).

## 1. What ships already, what is yours

- Expo SDK libraries and React Native bundle their own manifest. Found in a fresh SDK 58 app (`expo` 58, `react-native` 0.88):
  `expo-application` (FileTimestamp), `expo-constants` and `expo-system-ui` (UserDefaults), `expo-device` (SystemBootTime),
  `expo-file-system` (DiskSpace, FileTimestamp), React Native core and its Folly / boost / glog pods.
- Libraries without a manifest in their npm package (`react-native-keychain`, `@react-native-community/netinfo`,
  `react-native-screens`, `react-native-gesture-handler`, `react-native-reanimated`, `expo-secure-store`) had no required-reason
  symbol in their native sources. Native SDKs inside pods (the Sentry Cocoa SDK) ship their own manifest in the pod, which
  only a build shows.
- Yours: reasons for APIs your own native code or a static pod without a manifest uses, plus **collected data types**
  and tracking, which Expo does not infer.

Scan the installed dependency tree whenever dependencies change (add it to the PR checklist):

```sh
find node_modules -name PrivacyInfo.xcprivacy -not -path '*/Pods/*' -exec grep -H "NSPrivacyAccessedAPICategory" {} + | sort
```

A library that touches `NSUserDefaults`, file timestamps, `systemUptime` / `mach_absolute_time`, free disk space or
`activeInputModes` and has no manifest needs its category and an Apple-approved reason code in your config (copy it from the
library's documentation or its manifest). Apple's reason codes are listed in its "Describing use of required reason API" page;
Expo's guide (docs.expo.dev/guides/apple-privacy) says the same and notes Apple does not reliably read manifests of static pods.

## 2. The config

Type-checked against `ExpoConfig` (`ios.privacyManifests`, SDK 58):

```ts
// app.config.ts, inside ios: { ... }
privacyManifests: {
  NSPrivacyAccessedAPITypes: [
    { NSPrivacyAccessedAPIType: 'NSPrivacyAccessedAPICategoryUserDefaults', NSPrivacyAccessedAPITypeReasons: ['CA92.1'] },
  ],
  NSPrivacyCollectedDataTypes: [
    { NSPrivacyCollectedDataType: 'NSPrivacyCollectedDataTypeCrashData', NSPrivacyCollectedDataTypeLinked: false,
      NSPrivacyCollectedDataTypeTracking: false, NSPrivacyCollectedDataTypePurposes: ['NSPrivacyCollectedDataTypePurposeAppFunctionality'] },
    { NSPrivacyCollectedDataType: 'NSPrivacyCollectedDataTypePerformanceData', NSPrivacyCollectedDataTypeLinked: false,
      NSPrivacyCollectedDataTypeTracking: false, NSPrivacyCollectedDataTypePurposes: ['NSPrivacyCollectedDataTypePurposeAnalytics'] },
    { NSPrivacyCollectedDataType: 'NSPrivacyCollectedDataTypeUserID', NSPrivacyCollectedDataTypeLinked: true,
      NSPrivacyCollectedDataTypeTracking: false, NSPrivacyCollectedDataTypePurposes: ['NSPrivacyCollectedDataTypePurposeAppFunctionality'] },
  ],
  NSPrivacyTracking: false,
},
```

The example matches an app that sends Sentry crash and performance data and an opaque user id
(`react-native-observability`); `CA92.1` is "app-only preferences" for `UserDefaults` (what `AsyncStorage` and the
consent store use). Change the data types with the SDKs you actually ship: every analytics, ads, attribution or push vendor
adds entries, and `NSPrivacyTracking: true` plus `NSPrivacyTrackingDomains` is required if any data is used for tracking.
Keep the manifest, the App Store privacy label, the Play data-safety form and the privacy policy saying the same thing.

## 3. Proof

- `npx tsc --noEmit` type-checks the keys against `ExpoConfig`; a jest test loads the config and asserts the required-reason
  entry, the three collected data types, `NSPrivacyTracking: false` and that no type is flagged as tracking.
- `APP_VARIANT=production npx expo prebuild --no-install --platform ios` writes `ios/<App>/PrivacyInfo.xcprivacy` with exactly those
  `NSPrivacyAccessedAPITypes`, `NSPrivacyCollectedDataTypes`, `NSPrivacyTracking` false and an empty `NSPrivacyTrackingDomains`
  (checked on SDK 58). Delete `ios/` and `android/` afterwards; they are build output.

Device or Mac only, not verifiable here: the merged report of the final binary (Xcode, Product, Archive, then Generate Privacy
Report, which aggregates the pods' manifests) and Apple's own validation at upload.
