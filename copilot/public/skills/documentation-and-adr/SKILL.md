# Documentation & ADRs Skill (public)

Living documentation, kept under version control, regenerated by CI.

## 1. `README.md` (already produced by `create-repo`)

Must answer in under 60 seconds:
1. What the service does (one paragraph).
2. How to run it locally (`make up && make run`).
3. Where the API contract lives (link to OpenAPI / `springdoc`).
4. Where the architecture overview lives (link to `docs/ARCHITECTURE.md`).
5. Where ADRs live (link to `docs/adr/`).
6. Codeowner.

## 2. `CONTRIBUTING.md`

- How to set up the dev env (refers to `local-dev-experience`).
- Branching + commit-message convention (refers to `release-versioning`).
- Test policy (refers to `unit-tests`, `component-tests`, `integration-tests`).
- Definition of Done — every PR checks: tests pass, Spotless clean, no new
  SpotBugs HIGH, OpenAPI snapshot reviewed, ADR added if architectural.
- Review SLA.

## 3. `docs/ARCHITECTURE.md` + C4 diagrams

Three C4 levels are sufficient:

```
docs/
├── ARCHITECTURE.md
└── diagrams/
    ├── c4-context.puml      # who calls this service, what does it call
    ├── c4-container.puml    # processes (the service, DB, broker, …)
    └── c4-component.puml    # internal packages — usually generated from
                             # ArchUnit's slices (see code-structure)
```

Use **Structurizr DSL** or **C4-PlantUML**. Render in CI:

```yaml
- uses: cloudbees/plantuml-github-action@master
  with: { args: -tsvg docs/diagrams/*.puml }
```

Generated SVGs are committed to `docs/diagrams/_rendered/`; pre-commit
fails if `.puml` changed but the SVG was not regenerated.

## 4. `docs/adr/` — Architecture Decision Records

Capture *why*, not *what*. One file per decision, immutable once accepted.

Template: `docs/adr/template.md`

```markdown
# ADR-NNNN — <Title>

* Status: PROPOSED | ACCEPTED | DEPRECATED | SUPERSEDED by ADR-MMMM
* Date: YYYY-MM-DD
* Deciders: @alice @bob
* Tags: persistence, security, …

## Context
What problem are we solving? What forces are at play?

## Decision
What we chose.

## Consequences
Positive, negative, neutral.

## Alternatives considered
A, B, C — each with one paragraph on why not.
```

When to write an ADR:
- Choosing one technology over another (Kafka vs RabbitMQ, JPA vs jOOQ).
- Introducing a new cross-cutting pattern.
- Choosing a wire format.
- Disabling a security default.
- Deviating from a `public/` skill.

ADRs are **append-only**. Superseding an old ADR creates a new one.

## 5. `docs/SLO.md`

See `observability` §4 — the SLI/SLO table for the service.

## 6. Use-case diagrams

Generated from the controller + operation classes via `springdoc` and a
PlantUML render step:

```
docs/diagrams/
├── usecase-create-document.puml
├── sequence-convert-document.puml
└── …
```

For each public endpoint, ship one sequence diagram and one use-case
diagram. They live alongside the test for the use case so they get updated
in the same PR.

## 7. Generated docs index

`docs/README.md` lists every doc with a one-line summary so a newcomer can
navigate without `grep`.

## Do / Don't

✅ Documentation is code: lives in the repo, is reviewed in PR, is rendered
in CI.
✅ Every architectural choice has an ADR.
✅ Diagrams are text-first (PlantUML / Structurizr) so they diff in git.
❌ Never put architecture diagrams in Confluence or a slide deck "as the
source of truth" — they drift the day after the meeting.
❌ Never amend a past ADR; supersede it.
